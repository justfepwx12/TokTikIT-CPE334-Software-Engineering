## Reflection

การใช้ AI ช่วยร่างเอกสารชุด Spec-DD ของ Lab 4 (specification.md, api-spec.md, ui-spec.md, tests.md) ช่วยประหยัดเวลาในการจัดโครงสร้าง engineering contract ได้เร็วมาก โดยเฉพาะการร่าง 7-field contract (BR-22), Dashboard scoping/aggregation (BR-25/BR-26), Optimistic concurrency (BR-27 `version` + `If-Match` 409), Idempotency (BR-28 24h TTL + `@@unique([ticketId, key])`), สูตร pseudo-SQL 8 สูตร และ Planned-Test 35 rows ที่ต้องผูก AC-34–AC-59 ข้าม 4 ไฟล์พร้อมกัน แต่ผลลัพธ์รอบแรกยังไม่สมบูรณ์และต้องตรวจสอบอย่างละเอียดก่อนใช้จริง ปัญหาที่พบจริงใน Lab 4 นี้และต้องแก้ไขเองมีทั้ง response example ปิด object ผิด (`]` แทน `}`), `followUpRequired` เขียนว่า required แต่บอก default false, AC-45/row 17 เรียกร้อง `items: []` ทั้งที่ BR-26 บอก aggregated-only, `resolvedToday` นิยามด้วย `updatedAt` โดยไม่มี transition timestamp, follow-up นับแบบ any-true แทน latest-action (greatest `id`) จน drill-down ไม่ตรง metric, และ CTA routes ใน `tests.md` §4 เขียนเป็น `/tickets/new` กับ `/staff/tickets` ซึ่งไม่มีอยู่จริงใน `App.tsx` (ของจริงคือ `/create-ticket` กับ `/queue`) ทำให้ต้องไล่เทียบโค้ดจริงทีละจุดก่อนยืนยัน

พอถึง phase implement (Issue #125–#128 ทำด้วย OpenCode/Muse Spark) ปัญหาเปลี่ยนจากเรื่องเอกสารเป็นเรื่อง runtime/concurrency ที่อ่านสเปกอย่างเดียวไม่มีทางเจอ สโตร์ idempotency แบบ in-memory ถูก evict ที่ 1000 entries และหายหมดตอน restart (ผิด BR-28 24h), gate ค้างเมื่อ first-insert throw (ไม่มี settle), follow-up นับด้วย unbounded ID fetch ใน memory (ผิด AC-47), `resolvedToday=true` ทับ `status` ของ caller แทน intersect, expired-key cleanup ใช้ `delete` แล้วชนกันได้ 500 (ต้องเป็น `deleteMany` + unique replay), draft `Idempotency-Key` อยู่แค่ ref หายตอน remount/reload (ต้อง persist กับ draft), ticket-switch แล้ว response เก่า (Ticket A) มาแทนที่ Ticket B (ต้องมี generation guard ทุก handler), และ `migration-actions.test.ts` เขียน `where: { id: { in: afterIds } }` ทั้งที่ `afterIds` คือ Ticket IDs (ต้องเป็น `ticketId`) แถม leaked-check ดันใส่ `description` ซึ่ง `Ticket.description` มีอยู่แล้วตั้งแต่ Lab 2 ทำให้ล้มเสมอ ทั้งหมดจบได้เพราะรันเทสจริงทุกครั้งก่อนขอ review ใหม่ (pure units 16/16, migration 5/5, workflow 5/5, client 143/143, e2e 33 runs parsed, `tsc --noEmit`/build/lint/diff-check ผ่าน, DB-backed suites รันบน Docker `localhost:15432` จนเขียว)

สิ่งที่ตระหนักได้คือให้ AI ร่างแล้วต้อง verify ย้อนกลับ 3 ชั้นเสมอก่อนสร้าง pull request เทียบ labsheet/contract, เทียบโค้ดจริงใน repo, และรันเทสจริง (รวม DB-backed บน staging copy) ข้ามชั้นไหนไปจะกลายเป็นคอมเมนต์ reviewer จากเพื่อนกลับมาทุกครั้ง — Lab 4 นี้โดนตีกลับรวม 8 รอบ (spec 2, DB 1, API 2, UI 3) ก่อนได้ Approved ทุก PR
